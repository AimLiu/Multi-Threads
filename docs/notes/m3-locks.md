## 任务 3.1：ReentrantLock

### synchronized vs ReentrantLock 三增强

| 能力 | synchronized | ReentrantLock |
|---|---|---|
| 抢不到锁 | 无限死等（BLOCKED） | `tryLock()` 立即放弃 / `tryLock(t,u)` 限时等待 |
| 等锁期间可中断 | ❌ | ✅ `lockInterruptibly()` / `tryLock(t,u)` |
| 公平性 | 仅非公平 | 可选公平锁 |

- `tryLock()`：立即尝试，抢不到马上返回 false，**不等待**。
- `tryLock(3, SECONDS)`：限时等待；等待期间**可被中断**（抛 InterruptedException）——这就是"可中断抢锁"的实现形式；超时仍抢不到返回 false。
- synchronized 没有"抢不到就放弃"选项：拿不到就无限期 BLOCKED 死等，等锁期间不可中断（只有拿到锁后在 sleep/wait 里才可被中断）。

### 公平锁为什么慢

精确机制：公平锁要**维护队列顺序**——新来的线程即使锁空闲也不能直接抢（`hasQueuedPredecessors`），必须排队；每次锁交接都要"唤醒队首 → 从 WAITING 恢复 → 上下文切换"。非公平锁允许新线程在锁释放瞬间"刚好赶上"直接 CAS 插队，**省掉唤醒与上下文切换**，交接快得多。

饥饿：非公平下不断有新线程插队，队列中某线程可能长期轮不上。缓解：AQS 队列本身 FIFO，已在队列中的线程不会被后来的插队者越过，故饥饿存在但比纯抢占温和。

### 铁律：unlock 必须 finally

`lock()` 与 `unlock()` 之间抛**任何**运行时异常 → 写在最后一行的 unlock 执行不到 → **锁泄漏**。隐蔽后果：上层以为失败去重试，重试代码又抢不到那把永不释放的锁，整个子系统僵死。铁律写法：`lock()` 后紧跟 `try`，`unlock()` 只放 `finally`。

### 思考题结论

1. **tryLock() vs tryLock(3,SECONDS)**：前者立即返回不等；后者限时等待+可中断+超时放弃。synchronized 无此选项，拿不到锁无限死等。
2. **公平锁为什么慢 / 非公平何时饥饿**：公平锁按队列顺序发锁（锁空闲也不许新线程抢），每次交接付唤醒+上下文切换成本；非公平允许插队所以快，但持续插队可使队列中线程长期饥饿（AQS 队列 FIFO 使其不至于无限恶化）。
3. **unlock 不在 finally 的后果**：任何异常 → 锁泄漏 → 其他线程饿死、重试代码僵死。

## 任务 3.2：死锁——制造、诊断、预防

### 四个必要条件（精确背诵）

| # | 条件 | 含义 |
|---|---|---|
| ① | 互斥 | 资源一次只能被一个线程持有 |
| ② | 持有并等待（请求与保持） | 拿着 A 去要 B |
| ③ | 不可剥夺 | 资源不能被强行抢走 |
| ④ | 循环等待 | A 等 B、B 等 A，成环 |

破坏任意一条即可预防死锁；**工程上最常用：破坏④循环等待（全局锁排序）**。

> 易背串：不存在"阻塞等待"这个条件名——那是②持有并等待；④循环等待最不能漏。

### 诊断：jstack 实操

```bash
jps -l                          # 找 pid
jstack <pid>                    # 输出中搜 "Found one Java-level deadlock"
```

死锁报告里两个线程均 BLOCKED，互相 "waiting to lock" 对方持有的锁。看懂这段报告是面试与实战双刚需。

**死锁报告四步确认法**（JMC / jstack 通用）：

1. 两个线程状态均 BLOCKED（卡在抢监视器锁路上）。
2. 对照两线程的 `locked <0x...>` 与 `waiting to lock <0x...>`：A 持有的正是 B 在等的，B 持有的正是 A 在等的——锁地址交叉一致，就是**循环等待**的可视化铁证。
3. 栈顶精确到源码行（`synchronized (gatewayB)` 那行）——JVM 扫描锁持有图找环，不是猜的。
4. JVM 只报告、**不救治**：检测到死锁但绝不干预，只能重启进程。"只能预防、无法运行时自愈"是死锁最重要的工程启示。

对照实验：跑 DeadLockFixedDemo（锁排序版）再观察——无死锁报告、正常结束。

### tryLock + 释放重试 破坏的是哪个条件？

**③不可剥夺**：tryLock 失败后主动释放已持有的锁 = 资源在持有者无法推进时可以被还回池子，剥夺成为可能，环无法维持。超时本身还把无限期等待变有界，双保险。

**隐藏联系**：只加超时、不释放已持有的锁，死锁退化为**活锁**（双方都超时-重试、始终错开）。完整形态 = tryLock 超时 + 释放 + **随机退避**重试。

### 死锁 vs 活锁

| | 死锁 | 活锁 |
|---|---|---|
| 线程状态 | 阻塞、冻结不动 | 一直在跑、不停重试 |
| CPU | 不占（park 挂起） | 烧得飞起 |
| 状态变化 | 不再变化（需外部干预） | 一直变，但任务无进展 |
| 一句话 | 大家都停了 | 大家都忙着做无用功 |

活锁成因 = **对称性**：双方以同样节奏退让-重试，每次恰好再撞车。解法核心是**打破对称**：

1. **随机退避**（random backoff）：重试前 sleep 随机时间，节奏错开（以太网冲突退避同理，最常用）。
2. **锁排序**：根上消灭循环等待，死锁活锁一起防。
3. **重试次数上限**：超限转排队等待或失败告警。

> 降负载/扩节点只是降低撞车频率，没有打破"同步撞车"机制，不算活锁正解。

### 思考题结论

1. **tryLock+释放重试为何破坏死锁？** 破坏③不可剥夺（自愿释放=可剥夺）；超时使等待有界。注意只超时不释放会退化成活锁，需配随机退避。
2. **活锁与死锁区别？** 死锁=线程阻塞冻结、不占 CPU、状态不变；活锁=线程活跃重试、狂占 CPU、状态在变但无进展。活锁防法：随机退避/锁排序/重试上限。

## 任务 3.3：读写锁与 StampedLock

### ReentrantReadWriteLock

- 读读共享、读写/写写互斥。适合**读多写少**（设备配置、元数据缓存）。
- 写锁可降级为读锁（先写锁→再读锁→放写锁）；读锁**不能**升级为写锁（会死锁/永远等不到）。

### 读写锁什么时候不划算（推理链）

1. 读写锁要维护读/写两套状态，**每次加解锁都比普通互斥锁贵**（固定成本）。
2. 读多写少：读并发收益巨大，摊平成本 → 赚。
3. **写多读少：写写互斥+读写互斥，几乎每次都互斥，零并发收益 + 更贵的固定成本 → 纯亏**；且写锁压住读、读可能被饿。

**口诀：读写锁读共享的收益，只属于读多写少。** 写多场景直接用普通互斥锁反而更快。"要写准确就得独占"没错，但既然都在互斥，就不该为读写锁多付钱。

### StampedLock（JDK 8+）

- 额外提供**乐观读**：读时**完全不加锁**，读后 `validate(stamp)` 校验期间有无写发生，失败再退化为悲观读锁重读。
- `validate` 是纯读的版本比对（位运算级），比拿锁便宜——乐观读快的根源是读路径一次锁都不拿。
- 限制：**不可重入、不支持 Condition**；适合性能敏感的只读热点。
- 写锁用 `writeStampOptimistically` 场景外，标准套路：

```java
long stamp = sl.tryOptimisticRead();   // 乐观读（无锁）
V v = read();
if (!sl.validate(stamp)) {             // 有写发生 → 数据可能脏
    stamp = sl.readLock();             // 升级悲观读锁
    try { v = read(); }                // ★ 必须重读
    finally { sl.unlockRead(stamp); }
}
```

### 术语锚点：乐观并发控制家族

"乐观尝试 → 验证 → 失败走慢路径"与数据库乐观锁（版本号）、CAS 自旋同属一个思想家族：**先假定无冲突，事后验证，冲突再退化**。validate 失败后不重读直接返回旧值 = bug。

### 思考题结论

1. **读少写多读写锁划算吗？** 不划算。几乎全程互斥、零并发收益，还要付更贵的锁管理成本，且读可能被写饿；直接用普通互斥锁更快。
2. **乐观读期间被写，validate 返回什么？如何自愈？** 返回 false；升级为悲观读锁并在锁内**重新读取**（旧值可能脏），finally 释放。乐观读阶段本身不加锁。

## 任务 3.4：Condition——精确唤醒

### 核心：一把锁，多个等待队列

`wait/notify` 只有一个等待队列，notify 唤醒谁不可控；`Condition` 在**一把锁**上挂**多个条件队列**（notFull/notEmpty），signal 精确唤醒对应条件的线程。`await/signal` 必须持锁调用，否则 `IllegalMonitorStateException`。这正是 ArrayBlockingQueue 的内部实现。

### 为什么等待一律用 while 不用 if

醒来后条件可能**又不成立**，两个来源：

1. **虚假唤醒（spurious wakeup）**：JLS 明确允许 await/wait 在无人 signal 时自己醒来（底层 futex/condition variable 特性）——规范层面的依据。
2. **抢醒（signal 后、抢锁前条件被第三方破坏）**：两个消费者都 await 在 notEmpty → 生产者放一条并 signal → 两个都被唤醒 → 都要先重新竞争锁 → C1 抢到、消费掉、放锁 → C2 这才抢到锁从 await 返回，**但队列又空了**。用 if 则 C2 直接 removeFirst 崩溃；用 while 则 C2 重验条件、继续 await 睡回去。

**口诀：唤醒只代表"可能有货"，不代表"现在有货"——醒来必须重验条件。**

### 一把锁两个 Condition vs 两把锁各一个条件

本质：**Condition 依附于锁，所以两种结构真正的差异是等待者是否共享同一把锁**。

| | 一锁两条件（ArrayBlockingQueue 实现） | 两锁各一条件（LinkedBlockingQueue 实现） |
|---|---|---|
| 互斥范围 | put/take 全互斥（同一把锁） | put 与 take 可并行 |
| 唤醒 | signal 精确到对方阵营 | 需要 cross-notify 对侧 |
| 复杂度 | 简单安全 | 高（两锁协作、计数协调、近满/空时更绕） |
| 吞吐 | 中 | 高 |

一句话：**前者用一把锁换简单与安全（互斥但唤醒精确）；后者用复杂协调换操作并行（吞吐高但易错）。**这是 JDK 的真实演进路线。

### 思考题结论

1. **while 改 if 什么场景出错？** 多生产者多消费者 + signal：被唤醒者重新抢锁期间条件被他人破坏（抢醒），或无人 signal 的虚假唤醒；if 不重验直接操作 → 溢出/取空。while 醒来重验，不满足继续睡。
2. **一锁两条件 vs 两锁两条件本质区别？** 前者所有等待者共享一把锁、互斥访问整个缓冲区但唤醒精确（单锁双条件，ABQ 路线）；后者 put/take 各一把锁、操作可并行，吞吐高但要处理两锁协作（LBQ 路线）。

### 深挖：读写锁的加解锁到底比互斥锁多做了什么？

> 背景：ReentrantLock / ReentrantReadWriteLock 都建在 AQS 上（8.1 正式学），AQS 核心是一个 **volatile int state**，锁的全部状态编码在这一个数里。

互斥锁的 state 只有"0=没人用 / 非0=被谁持有（含重入）"；读写锁同一时刻要表达"读者集合 + 写者"，五笔额外开销：

1. **state 劈两半**：高 16 位=读计数，低 16 位=写重入数。每次操作都要移位/掩码编解码，一次 CAS 还要保证两半不被改乱。
2. **读者之间抢同一个字（最大开销）**：读锁逻辑共享、实现上所有读者对**同一个 state** 打 CAS → N 个读者就 N 次 CAS 打同一个缓存行 → **缓存行乒乓**（2.5 同款）。互斥锁只在真冲突时竞争；读写锁的读者们和睦却要为计数打架。
3. **每线程簿记**：读锁重入需要知道每个线程各持几次 → ThreadLocal HoldCounter，每次加解锁查/初始化/减/清（防泄漏）。互斥锁无此层。
4. **入队看队列脸色**：防写者饿死，非公平模式下读者加锁前也要 `readerShouldBlock()` 检查队首是否写者。互斥锁非公平只管"空闲就抢"。
5. **解锁唤醒决策**：互斥锁唤醒下一个节点完事；读写锁要判断"读计数归零该叫写者？写解锁该成串叫醒读者？"——AQS 共享模式的传播唤醒更复杂。

另外：synchronized 无竞争时有偏向锁/轻量级锁优化（8.4），近乎一次对象头 CAS，比互斥锁还便宜。

**结论**：五笔开销每次加解锁都付；只有"读读并发"的收益能摊平它们 → 读写锁只属于读多写少。

| 环节 | 互斥锁 | 读写锁 |
|---|---|---|
| 状态编码 | 一个数 0/非0 | int 劈两半+位运算 |
| 加锁 CAS | 仅冲突时竞争 | 读者之间也竞争同一字 |
| 每线程簿记 | 无 | ThreadLocal HoldCounter |
| 入队前检查 | 空闲直接抢 | 查队首是否写者 |
| 解锁 | 唤醒下一个 | 决策唤醒写者/成串唤醒读者 |
