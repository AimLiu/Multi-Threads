## 任务 6.1：ThreadPoolExecutor 参数与执行流程

### 七参数与执行流程（必背）

corePoolSize / maximumPoolSize / keepAliveTime+unit / workQueue / threadFactory / rejectedExecutionHandler。

**流程：来了任务 → ①核心未满：建核心线程；②核心满：入队；③队列满：建非核心（到 max）；④队列满且 max 满：拒绝策略。**

⚠️ 是"先入队再扩容"，不是"先扩到 max 再入队"——高频认知误区。实测验证：8 任务（core2+queue10）→ 只见 2 线程；16 任务（>12）→ 扩到 4；17 任务 → AbortPolicy 抛异常。

### 拒绝策略四种 = 过载时系统的"人格"

| 策略 | 行为 | 人格 | 适用 |
|---|---|---|---|
| Abort（默认） | 抛 RejectedExecutionException | 宁可炸给你看 | 快速失败+上游重试 |
| CallerRuns | 提交者自己执行 | 大家一起慢（反压） | 不允许丢的任务 |
| Discard | 静默丢 | 丢卒保车 | 可丢的日志/指标 |
| DiscardOldest | 丢队首最老的 | 新的更重要 | 时效性数据 |

### 思考题结论精解

**Q1：先入队再扩容，何时省、何时害？**

- 省：短平快任务排队损耗小，不必为瞬时就绪的任务开新线程（线程是贵资源：栈内存+创建切换成本）。
- 害一：长任务+时限要求 → 任务压在队列出不来。解法"核心=max"是放弃突发吸收换响应，有代价。
- 害二（更隐蔽，快慢混合）：2 个核心线程被慢任务（等 ACK 30s）占死，快任务（5ms 计算）陪绑。光调核心数没用，正解是**池隔离**（快慢任务各一个池，6.2）。

**Q2：指令下发池怎么设？**

标准答案：**有界队列 + CallerRunsPolicy**，核心=max 按网关承诺的并发上限设（如 8），队列深度=突发缓冲预算（如 1000）。

- 为什么必须有界：无界 = 拒绝策略**永远无法触发**（触发条件是"队列满且线程到 max"）+ 线程永不扩容 + 渐变型 OOM——**无界队列同时废掉线程池两道安全机制，是静音炸弹**（5.2 呼应）。
- CallerRuns 的反压原理：提交者被拖慢 → 上游产指令速率跟着降 → 系统减速不雪崩。
- **CallerRuns 的隐藏代价**：执行者=提交者线程。提交者是 Netty EventLoop/事件线程时，跑 30s 任务会冻结该线程上所有连接——此时宁选 Abort+上层重试。**"谁提交的"决定 CallerRuns 是妙药还是毒药**。

## 任务 6.2：自定义线程池三件套

### ThreadFactory 的两个职责

1. 命名（jstack 排障时能看懂）。
2. **UncaughtExceptionHandler = 异常的终点站（最后接盘侠），不是"抛出的格式"**：任务异常无人 catch → 落到 JVM 默认 handler（一行 stderr，线程默默死）→ setUncaughtExceptionHandler 替换成自定义日志+告警。触发时机是线程死亡时；池会自动补新 worker（异常不使池缩水），但要靠 handler 才知道"刚才有任务炸了"。

### shutdown vs shutdownNow（必背）

| | 队列中未执行的任务 | 活跃线程 |
|---|---|---|
| shutdown() | **全部执行完**（关门谢客：在跑的+排队的都跑完） | 等自然结束 |
| shutdownNow() | **作为 List 返回给调用者**（不做了，剩下的还给你→可落库/重发/补偿） | 全部 interrupt |

- interrupt 没有"失败"一说；真正停不下是因为**任务不响应中断**（不查标志、无可中断阻塞点）——"中断是协作式"（1.3）在池上的回响。shutdownNow 是"请求停止"，任务不配合就停不下。
- 优雅关闭三步连招的原因：`shutdown → awaitTermination(超时) → shutdownNow` = 给体面的机会，超时不体面（中断+收尾清单）。

### 池大小经验与隔离

- CPU 密集 ≈ N+1；I/O 密集 ≈ N × (1 + 等待/计算)；压测验证。
- **池隔离（舱壁模式）**：快慢任务各一个池，防"快任务被慢任务绑架"（6.1 害二的正解）。
- 快任务也可能变慢（网关掉线）→ 不推翻分池，而是**每条链路都要有超时兜底**。

### 思考题 2 精解：真实架构对照（用户公司 Kafka+MQTT 方案）

```
下发链：业务 → Kafka（削峰/解耦）→ 下游消费者 → MQTT 发布（快动作，毫秒级）
回执链：设备 ack → MQTT topic → 下游订阅 → 转发 Kafka → 回调原调用方
```

**核心思想："把慢从任务里拆出去"**——池只跑"投递"这个快动作，"等 ACK"是独立订阅 topic 的异步等待，**不占线程池的线程**。对照课程内组件：

- Kafka ↔ 7.2 的 BlockingQueue（进程内→跨进程版，多持久化/重放）
- 异步等 ACK（订阅回调）↔ 7.3 的 orTimeout+exceptionally（超时交给机制而非线程死等）
- 若仍有"同步死等 ACK"路径 → 那才是快慢绑架的根源，改造方向 = 全异步化

### 思考题结论

1. **shutdown/shutdownNow 对队列任务？** 前者全跑完；后者 interrupt 活跃线程 + 未执行任务 List 退还。停不下不是因为 interrupt 失败，是任务不响应中断。
2. **快慢两类任务池怎么设？** 分池（隔离）。慢池 core=max+有界+CallerRuns；快池按公式起点+压测定参；每条链路带超时。更优架构：慢等待拆出线程（异步回调/消息回流），池只跑快动作。

## 任务 6.3：ScheduledExecutorService 定时任务

### 头号大坑（实测）

任务抛出未捕获异常 → **后续所有执行被静默取消**，无任何报错。心跳任务挂了毫无感知 = IoT 经典事故。修法：任务方法体 try-catch 全包。对照：DelayQueue 自管循环时忘了 catch 会直接杀死消费线程（死得更响）——两种方案各有各的坑。

### fixedRate vs fixedDelay：计时起点不同

| | scheduleAtFixedRate | scheduleWithFixedDelay |
|---|---|---|
| 下次计时起点 | 上次**开始**时刻 | 上次**结束**时刻 |
| 意图 | 每 N 秒一次（节奏对齐钟表） | 做完歇 N 秒（节奏跟随任务） |
| 任务耗时 < 周期 | 两者几乎重合（"感觉一样"的原因） | 同左 |
| 任务耗时 > 周期 | 不并行；补跑/追赶，失去间隙 | 天然顺延，永远有 N 秒喘息 |

**口诀：rate 对齐钟表，delay 对齐任务。**

心跳超时扫描选 **fixedRate**：离线判定依赖扫描间隔稳定（间隔漂移 → 检测精度崩）。扫描可能超周期时正解是**把单轮扫描做快**（分桶/时间片，7.1 进阶点），不是迁就调度器换 delay。**要节奏稳定选 rate，要保证休息选 delay；任务超周期先修任务。**

### DelayQueue vs ScheduledExecutor：架构位置不同

| | ScheduledExecutor | DelayQueue |
|---|---|---|
| 拿到的是 | **执行器**（线程/调度/重试全托管） | **数据结构**（只有排序+到期阻塞） |
| 消费循环 | 框架内部有，只管 submit | **自己写**（take→处理→重入队） |
| 动态改计划 | 弱（cancel 重提） | 强（出队改 dueAt 重新 offer） |
| 出错兜底 | 6.3 静默取消坑 | 循环自己管 = 异常自己兜 |

**取舍口诀：标准定时需求（心跳/轮询/刷新）用 ScheduledExecutor，别造轮子；"延迟"是业务状态的一部分（指数退避、到期改计划、与业务队列耦合）用 DelayQueue。** 第三条路：CF 生态的 delayedExecutor（练习 6 用过）。

### 思考题结论

1. **心跳扫描 rate 还是 delay？** fixedRate（检测精度依赖间隔稳定）。扫描可能超周期 → 修任务（分桶扫描），不迁就调度器。
2. **DelayQueue vs ScheduledExecutor？** 执行器 vs 数据结构：标准定时交给前者；延迟随结果变化、要改计划重入队时用后者（循环和状态归自己管，代价是异常自己兜）。

## 任务 6.4：ForkJoin 与并行流

### 实测反转：串行 64ms / 并行流 86ms / ForkJoin 180ms——为什么

- 串行 64ms 是**假的对照组**：规则内存顺序加法被 JIT **向量化/循环展开**（SIMD 一次加 4~8 个 long），64ms 是深度优化后的极限，不是朴素累加。
- FJ 180ms 的账单：1 万个子任务对象 + fork/join 队列操作 + join 线程协调——任务本身（1 万次加法 ≈ 微秒级）比管理成本还轻。**搬一块砖雇项目经理，协调费比砖贵。**
- 并行流居中：LongStream.Spliterator 专门优化 range 分割（不装箱、不手写任务类），比手写 FJ 懂行。

**读法三结论：**
1. FJ 收益条件 = **每块任务足够重**（THRESHOLD 1万→100万，子任务 1万→100 个，FJ 明显改善——实测可验证）。
2. 快任务+规则数据 → JIT 向量化 + 单线程缓存友好就是天花板，多线程反而交协调税。
3. **并行不是默认更快**：任务重 + 数据不规则/计算密集才更快。

### ForkJoinPool 两大发明（针对的痛点：分治在普通池上死锁）

普通池跑分治：所有线程卡在 join 等子任务，子任务在队列里没人跑（**线程饥饿死锁**）。

**发明一：工作窃取**。每线程自己的双端队列：自己从**队头** LIFO 取（小任务热乎、缓存友好）；空闲线程从别人**队尾** FIFO 偷（偷最大最老的任务块）。效果：①负载自动均衡；②join 等待时线程不傻等——转头跑自己队列里的子任务（helping）→ 直接消灭饥饿死锁；③队列按线程分散，竞争小。

**发明二：RecursiveTask 把分治表达成任务**。compute() 惯用法：

```java
if (够小) return 直接算;
left.fork();                  // 左半入我的队列（可能被偷）
return right.compute() + left.join();   // ★ 右半当场算：当前线程反正闲着，
                                        //   少一次任务调度；join 时去帮忙而非干等
```

**ForkJoinPool.commonPool()**：JVM 全局共享（并行度=核数-1），为 CPU 密集设计——4.3"commonPool 灾难"（I/O 占 CPU 槽位）的主角。

### 思考题结论

1. **为什么 left.fork(); right.compute() 比 fork 两次好？** 右半当前线程当场算，省一次任务调度/入队；join 期间线程还会 helping 别的子任务。fork/join 有代价，能自己算的不排队。
2. **parallelStream 里 sleep(5000) 的灾难？** commonPool 容量=核数-1 且全 JVM 共享：几个阻塞 I/O 任务占满槽位 → 所有并行流/默认 CF 全局排队（m4 讲过的灾难组合）。

## 任务 6.5：虚拟线程（JEP 444，Java 21 正式）

### 实测对照（本机）

- `newFixedThreadPool(100_000)`（平台线程）：久久不结束、内存持续上涨——1MB 栈 × 10 万的理论需求，实际边建边挂起地硬撑。
- `newVirtualThreadPerTaskExecutor()`：10 万任务 4172ms 完成，载体是 ForkJoinPool-1-worker-N（专门的调度池，并行度=核数）。

### 是什么：线程从贵资源变成廉价对象

平台线程贵在两处：创建贵（系统调用 + ~1MB 栈）、**阻塞贵**（卡在 I/O 上，1MB 内存 + 内核调度槽白占——6.1/6.2 调池本质是给"稀缺的阻塞能力"配给）。虚拟线程 = JVM 管理的普通 Java 对象（栈存堆上、按需增长、初始几百字节~几 KB），mount 到少量载体平台线程上运行。

### 怎么工作：阻塞点 = 换人的机会

虚拟线程阻塞在 I/O（socket/sleep/JDBC 等）→ JDK 内部**自动 unmount**：栈快照存到堆上（**continuation：栈可搬走可恢复**——内核线程做不到），载体立刻跑别的虚拟线程；I/O 完成后 mount 回某个载体继续。sleep 对虚拟线程只是"挂起对象"，没有内核线程陪等。

### 心智模型切换表（最重要）

| | 平台线程时代 | 虚拟线程时代 |
|---|---|---|
| 线程是什么 | 稀缺资源（几十~几百） | 廉价对象（百万级） |
| 并发策略 | 池化复用、精心调参 | 每任务一个，**不池化** |
| 写法 | 被迫异步回调 | **同步阻塞写法**，吞吐接近异步 |
| 6.1/6.2 的纠结 | 核心/队列/拒绝策略 | 大部分 evaporates |
| 该想的问题 | "线程够不够用" | "共享状态对不对"（正确性） |

### 用/不用/别用

- ✅ I/O 密集 + 高并发：每设备一线程、每请求一线程、批量调外部接口、等 ACK。
- ❌ CPU 密集：核数不变，算不快，反而多 mount/unmount 开销。
- ⚠️ ThreadLocal 滥用的代码：百万线程 × 每线程上下文 = 内存放大（8.3）。

### 两个生产红线

1. **synchronized 内阻塞 = 钉住载体（pinning）**：Java 21 中无法 unmount，载体白占一个核；高并发老代码迁虚拟线程可能不升反降。热点路径 synchronized → ReentrantLock。（JDK 24 / JEP 491 已修复。）
2. **不池化虚拟线程**：`newVirtualThreadPerTaskExecutor` 名字即答案——池化等于把廉价对象重新当稀缺资源管。

### 与 Netty 的关系

Netty（事件循环+回调）与虚拟线程解决同一个问题（高并发 I/O）的两条路线：前者性能极致但回调地狱；后者**同步写法获得接近吞吐**。成熟 Netty 接入层不必动；简化收益最大的是**业务层异步编排**（下发→等 ACK→更新状态的 CF 链/消息回调胶水可消失，回到"一设备一虚拟线程、从上到下读得懂"的代码形状）。

### 思考题结论

1. **虚拟线程解决共享状态竞争吗？** 不。**虚拟线程解决吞吐（资源），不解决正确性（竞争）**——10 万虚拟线程写同一 HashMap 照样丢数据。正确性永远靠锁/原子类/并发容器（模块 2~5）。
2. **Netty 异步项目迁 Java 21 怎么简化？** 连接处理可写回"一设备一虚拟线程 + 同步 read/write"；业务编排的回调/CF 胶水大量消失；接入层 Netty 可保留。
